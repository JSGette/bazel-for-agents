# Declare artifacts and register their producing actions

Use this page to implement a small file-producing rule. Its worked example uses
template expansion and file writing. External tools, compiler toolchains, and
remote execution require additional, task-specific guidance.

## Follow the artifact through the rule

1. Obtain input `File` objects from dependency attributes or providers. A `File`
   represents an artifact; it does not expose its contents for analysis-time
   reading. [File semantics][files]
2. Declare the output artifact, for example with `ctx.actions.declare_file()`.
   Declaration returns a `File`; it does not write the output. Register a
   producing action separately. [Action API][action-api]
3. Register the action with its input and output artifacts. An action records
   work to perform later; registration itself does not execute that work.
   [Action semantics][actions]
4. Expose the result through the rule's appropriate provider and default-output
   interface. Bazel selects work from the requested output graph.
   [Output selection][outputs]

Every generated file must have a producing action. The rule guide specifies
exactly one producing action per generated file; source files are inputs, not
action outputs. [File semantics][files]

## Choose an action with the required behavior

| Need | API | Coverage here |
| --- | --- | --- |
| Write analysis-known text to a file | `ctx.actions.write()` | Used for the fixture's metadata. |
| Replace text in a template file | `ctx.actions.expand_template()` | Used for the greeting and report. |
| Run an executable tool | `ctx.actions.run()` | API definition inspected; no process-spawning example in this page. |

These operations are defined in the [action API][action-api]. For the first two
tasks, our recommendation is to use the built-in operation directly. It keeps the
example's contract small and avoids introducing an unrelated tool dependency.

`expand_template()` accepts an input template `File`, output `File`, and replacement
dictionary. It performs replacements when the action executes. The template can
itself be generated by another action. The fixture exercises precisely that
input-to-output chain. [Expansion API][expand], [observed results][execution]

## Read the working example

Open [defs.bzl](../examples/foundations/defs.bzl) alongside
[BUILD.bazel](../examples/foundations/BUILD.bazel):

```text
message.tpl ──TemplateExpand──> greeting.txt ──TemplateExpand──> report.txt
                         separate FileWrite ──> greeting.metadata.txt
```

The producer substitutes the person's name. The consumer obtains the generated
message through `GreetingInfo` and uses it as its template. There is no attempt to
read the generated text during analysis. The metadata action is registered but
its output is requested separately. [Fixture and results][execution]

## Keep action dependencies explicit

For an external-tool action, `run()` has distinct `inputs`, `outputs`, `executable`,
`tools`, and `arguments` parameters. Passing a path as a command-line argument is
not itself an input declaration. Supply the artifacts the action reads through
its input/tool interfaces. The API also documents when a tool's runfiles are
added automatically; do not assume an arbitrary executable path supplies them.
[Action API][action-api], [input contract][actions]

Actions must produce their declared outputs. The documented action contract also
requires declaring inputs; our recommendation is to review that contract before
optimizing a rule. A successful local command outside Bazel is not a verification
of the action's declarations. [Action contract][actions]

## Verify the action graph and the result

The [foundation record][execution] contains exact `aquery` and build commands.
`aquery` showed two `TemplateExpand` actions connected by `greeting.txt`, plus the
metadata `FileWrite`. The build produced `Greetings, Bazel!` followed by a newline.
Both observations matter: the graph describes registered work, while checking the
file establishes the observed result. [aquery reference][aquery]

runtime coverage. This fixture does not establish subprocess, sandbox, caching,
toolchain, directory-expansion, or remote-execution behavior.
