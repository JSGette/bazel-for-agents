# Choose the narrowest dependency override

Use an override for a deliberate, reviewed dependency change that ordinary module
selection or the extension's documented API does not express. Record why it is
needed, the exact source identity, and when it can be removed. These are this
reference's maintenance recommendations. Overrides change dependency semantics;
they are not a generic way to suppress resolution errors.

## Choose the layer being changed

| Need | Mechanism |
| --- | --- |
| Pin a registry module version, change its registry, or apply source patches | `single_version_override` |
| Permit a selected set of versions of one registry module to coexist | `multiple_version_override` |
| Replace a module with an archive, Git source, or local checkout | `archive_override`, `git_override`, or `local_path_override` |
| Replace a repository generated by an extension | `override_repo` |
| Add an existing repository to an extension's visible repository set | `inject_repo` |

[Directive implementations][globals], [module override model][module]

Module overrides are effective only in the root module; overrides in a dependency
are ignored. A root override can target a transitive module without introducing
it as a direct dependency. It changes resolution or the chosen source but does
not automatically import that module's apparent name into the root.
[Root scope][module], [repository visibility](repository-mapping.md)

## Keep registry semantics when that is sufficient

`single_version_override` can set `version`, `registry`, and/or patch attributes.
Omitting `version` allows a registry or patch override without pinning the selected
version. A version pin applies across module requests in the graph; compatibility
with all consumers still needs verification. [Single-version API][globals]

`multiple_version_override` permits only the listed versions, which must already
occur in the discovered graph before selection. Dependencies are raised to the
nearest allowed version that is at least as high as their request; a remaining
request above all allowed versions fails. It does not cause arbitrary missing
versions to be discovered. [Selection implementation][selection]

At this baseline, `compatibility_level` and `max_compatibility_level` are no-ops.
Do not rely on those parameters to isolate incompatible versions or make an
allowlist safe. Coexisting repository versions still require an integration design
for their targets, providers, and runtime libraries. The need to verify that design
is our recommendation, not a module-system compatibility guarantee.
[Actual manifest implementation][globals]

## Pin replacement sources and retain the module contract

Non-registry overrides obtain the module manifest from the replacement source
rather than selecting that module's source from a registry. They remove the
module from ordinary registry version selection. `archive_override` delegates to
an HTTP archive repository rule; `git_override` delegates to a Git repository
rule; `local_path_override` uses a local repository directory.
[Override implementation][globals], [non-registry model][module]

Use an immutable Git commit or a digest-verified archive for a shareable override.
Use a local path for an intentional local checkout and document that machine-local
input. Preserve a valid `MODULE.bazel` and inspect its dependencies; replacing
source content does not mean all consumers have been tested against it. These
are this reference's source-review recommendations.

## Make patches reviewable and portable

`single_version_override(patches = ...)` takes labels for patch files in the root
project and applies them in list order. `patch_strip` controls removal of path
components. Patches supplied by the root can change the dependency's
`MODULE.bazel` used during module processing. [Patch API and label validation][globals],
[patch tests][overrides-tests]

`patch_cmds` run Bash commands after patches on Linux/macOS. Changes they make to
`MODULE.bazel` do not affect module resolution. Prefer a reviewed patch file when
the change is a textual source modification, and avoid presenting a Bash patch
command as a cross-platform recipe. [Patch-command contract][globals]

## Handle extension-generated repositories explicitly

`override_repo` replaces a repository the extension defines with a repository
already visible to the root. `inject_repo` supplies a new repository under an
extension-side name instead. For both directives, keyword **keys name the
repository inside the extension**, and values name repositories visible to the
root. Both are ignored outside the root and when `--ignore_dev_dependency` is
enabled. [Extension override/injection APIs][globals]

An extension may offer a domain-specific tag for patching a language package;
check that API first. A language package is not automatically a Bazel module,
so its package name is not necessarily a valid `module_name` for module overrides.
Module extensions can resolve non-Bazel ecosystems and create repositories from
that result. [Extension model][extension]

After any override, review the resolved module graph, generated repository
definitions, lockfile change, and relevant consuming builds. Keep diagnostics
focused on the affected layer: module selection, extension policy, repository
fetch, or target analysis. See [lockfile maintenance](lockfile-and-vendor.md) and
[repository mappings](repository-mapping.md).
