# Resolve repository names in the right context

Use this page when `@name` is unknown, a label resolves differently in another
repository, or an extension-generated dependency seems inaccessible. Start with
the repository containing the reference, then inspect what names that repository
imports. [Repository names][overview], [mapping implementation][mapping]

## Separate dependency identity from local spelling

| Name | Role |
| --- | --- |
| Module name | Identity used by module dependency resolution. |
| Apparent repository name | Name interpreted through the referencing repository's mapping. |
| Canonical repository name | Unambiguous repository identity within the build; formatting is not a public API. |

A `bazel_dep` defaults its apparent name to the module name; `repo_name` changes
that local import. Renaming an import does not rename the module for resolution,
and another dependent can choose a different apparent name. `use_repo()` can also
import an extension-generated repository under a local alias.
[Module naming][module], [directive implementation][globals]

For keyword `use_repo` imports, **local name = exported name**. For keyword
`override_repo` and `inject_repo` arguments, the direction is different:
**extension-side name = name visible to the root module**. Check the API being
edited rather than generalizing one alias direction to another directive.
[Argument contracts][globals]

## Apply the referencing repository's visibility

A module sees the repositories declared by its direct `bazel_dep` dependencies
and imported with `use_repo`, plus repositories declared for itself through
`use_repo_rule`. It does not gain arbitrary transitive module names. Add the
appropriate direct import instead of using a guessed `@@...` name to bypass the
missing dependency declaration. [Strict dependencies][module], [direct rule proxy][globals]

An extension-generated repository can see the repositories visible to the module
hosting the extension and the sibling repositories generated by that extension.
It does not automatically inherit all imports of the root module. Different
extensions have separate generated-repository namespaces.
[Generated-repository visibility][extension]

When a generated sibling name conflicts with a repository already visible to the
hosting module, mapping and label-construction context matter. In an extension
implementation, constructing a `Label` resolves it in that implementation's
context before handing it to a repository rule; plain label strings can refer to
generated siblings. Avoid conflicting public names where possible, and inspect
the final mapping when the distinction is unavoidable.
[Conflict semantics][extension], [mapping construction][mapping]

Repository visibility is separate from target visibility and `.bzl` load
visibility. A mapped `@name` is necessary for interpreting a label, but does not
grant access to every target or extension file in that repository. Continue to
[visibility](../core/visibility.md) once the repository itself resolves.
[Visibility claim evidence](../verification/core-visibility.md)

## Ask Bazel for canonical identities

Use supported APIs instead of reconstructing canonical names:

| Situation | Supported interface |
| --- | --- |
| Already have a Starlark `Label` | `Label.repo_name` exposes its canonical repository name. |
| External inspection tool | `bazel mod dump_repo_mapping` exposes apparent-to-canonical mappings. |
| Need a repository's creation definition | `bazel mod show_repo` shows the resolved repository rule. |
| Runtime data lookup | Use the language's repository-aware runfiles library and the documented runfiles path interface. |

[Module naming guidance][module], [module command implementation][mod-command],
[repository inspection][mod]

A path embedded in a binary should not be assembled from a guessed canonical
repository directory. The module guide points to `$(rlocationpath ...)` and
repository-aware runfiles libraries for this boundary. Choose the implementation
supplied by the current language ruleset; use its exact release's runfiles API.
[Runfiles naming guidance][module]

If a diagnostic prints a canonical label, it is useful evidence for that build,
not a naming scheme to copy into maintained source. Keep the user-facing import
stable through apparent names and recheck mappings after dependency changes.
This last paragraph is the reference's maintenance recommendation.
