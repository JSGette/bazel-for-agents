# Test a rule across the Bazel invocation boundary

Use an integration fixture when the behavior includes module resolution, repository
creation, package loading, toolchain selection, real tool execution, or the combined
consumer experience. This page proposes a review method; it does not introduce a
new test harness or CI system.

## Choose the smallest complete boundary

Our recommendation is to use these layers together:

| Behavior under review | Appropriate boundary |
| --- | --- |
| Pure Starlark transformation | A unit-test callback with explicit values. |
| Provider, output, action, or configuration contract | An analysis test. |
| Generated bytes or runtime behavior | A language test consuming declared artifacts. |
| Loading/module errors or a full rule installation | A separate controlled Bazel invocation. |

Bazel's analysis-test interface reports configured results and cannot register
normal actions. That makes it useful for rule contracts, but it does not replace
checks of phases that fail before such a result exists or of the tool's execution.
[Bazel analysis-test API][rule-api]

For a full consumer fixture, our recommendation is a small module that depends on
the library as a user would. Pin Bazel and dependency selections, preserve the
resolved lockfile, and declare every toolchain/platform needed by the case. Keep
fixtures independent enough to expose missing setup instead of inheriting a large
maintainer checkout's configuration.

## Assert both success and the intended result

Our existing [foundations fixture](../examples/foundations/verify.py) checks distinct
contracts: the requested output contents, the registered action chain, the
selection of optional outputs, and rejection of a dependency missing a provider.
Its [execution record](../verification/foundations.md) states the exact version,
commands, environment, and limits. Those observations establish only that fixture's
behavior, not compatibility with every ruleset or platform.

For a negative case, our recommendation is to require a nonzero result and the
specific diagnostic explaining the intended failure. A failure caused by an
unavailable download or missing compiler must not satisfy an assertion about
visibility, provider requirements, or malformed module configuration.

Use a fresh output location when the assertion depends on the absence of an output
before a request. For other cases, preserve normal incremental behavior and test
the intended dependency change directly. Avoid indiscriminate cache deletion as
an unexplained test setup step.

## Record the configuration that gives the result meaning

Our recommended evidence record includes source commit, exact Bazel binary,
resolved module graph, tool/SDK versions, execution and target platforms, relevant
flags, rc-file policy, non-secret environment, assertions, and observed outputs.
Document any deliberate host dependency.

A passing test result may be cached according to Bazel's test-result policy.
Disabling test-result reuse is a different question from whether the test's build
actions were rerun. Record the distinction rather than interpreting any successful
invocation as fresh execution of every dependency. [Test-result option][test-options]

For configuration or remote integration tests, isolate semantic flags from transport
and reporting settings. A harness that ignores rc files must deliberately account
for any reporting configuration it otherwise would have inherited. Keep credentials
outside fixtures and logs.
