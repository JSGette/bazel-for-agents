# Test generated contents and runtime behavior

Use an execution test when correctness depends on generated bytes, the behavior of
an executable, or runtime data lookup. An [analysis test](analysis-tests.md) can
check the planned action but cannot establish that its tool produces the intended
result.

## Put the tested output in the runtime input contract

Choose the appropriate language ruleset's test rule. Make the artifact or program
under test a declared dependency using that rule's supported runtime interface.
Tests access inputs through runfiles or another explicitly supported input
mechanism; they must not assume access to the source checkout. Runfiles can use
symlinks and must not be modified. [Test environment contract][encyclopedia]

Our recommendation: use the language's supported runfiles library to find data.
Avoid manufacturing an absolute output path from a local build tree. Keep runtime
path handling separate from checking the output's semantic contents.

Use `TEST_TMPDIR` for test scratch files. Use `TEST_UNDECLARED_OUTPUTS_DIR` when a
diagnostic artifact should be collected with the test results. The presence of a
writable temporary directory does not authorize writing into runfiles or relying
on the invoking user's home directory. [Environment and filesystem contract][encyclopedia]

## Assert the product behavior

Our recommendation is to compare the smallest observable property that expresses
the contract: generated content, schema validity, command exit status, archive
entries, or the behavior of a compiled program. Include empty inputs, names with
spaces, and failure cases when they matter for that tool. An existence check alone
is weak evidence for a code generator whose output could be empty or malformed.

The test process must complete successfully within its timeout. `size` and
`timeout` describe related but different scheduling/runtime expectations; an
explicit timeout can override the size-implied timeout. Choose them for the actual
test workload and report useful diagnostics before failure. [Runner contract][encyclopedia]

Tests should depend on the specified test environment, not arbitrary ambient
variables. Time and date are not fixed by the test contract. Make seeds, time
sources, locale-sensitive behavior, and external service inputs explicit when
they affect assertions. These are test-design recommendations based on the stated
environment boundaries. [Initial conditions and host resources][encyclopedia]

## Make runner features explicit

Setting a shard count is not enough to distribute cases correctly. A sharding-aware
runner uses `TEST_TOTAL_SHARDS` and `TEST_SHARD_INDEX` to choose cases and creates or
updates `TEST_SHARD_STATUS_FILE` to signal support. Verify that the selected test
framework implements this contract before enabling sharding. [Sharding contract][encyclopedia]

Bazel 9.3.1 defaults `--cache_test_results` to `auto`. Its rules include rerunning
when dependencies change, the test previously failed, multiple runs were requested,
or the test is marked external. `yes` and `no` change the policy. A reported cached
result is evidence of reuse, not of a fresh test process in that invocation.
[Option definition][test-options]

Our recommendation: record whether results were executed or reused when making a
new verification claim. A cross-compiled binary may require a compatible execution
environment; a successful analysis of it is not evidence that it ran on the intended
target platform. Keep build, execution, and platform observations separate.
