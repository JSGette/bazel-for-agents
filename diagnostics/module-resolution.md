# Diagnose module and repository resolution

## Use this when

Use `bazel mod` to distinguish a requested module version, the resolved module
graph, an extension usage, and a generated repository. Read
[module selection](../modules/dependencies-and-version-selection.md) first.

## Follow the resolution layer

| Question | Mod subcommand or option |
| --- | --- |
| Which module versions survived selection? | `graph` |
| Why is a module reachable? | `path` or `all_paths`, with an appropriate `--from` scope |
| Why did a requested version change? | `explain`, with `--include_unused` and verbose detail when needed |
| Which repositories are generated by an extension and where is it used? | `show_extension`; graph `--extension_info` for related views |
| What repository definition resulted? | `show_repo`, in the correct base-module context |

These commands expose different layers. `--include_unused` includes modules
removed by resolution; do not mistake those entries for the selected version.
`show_repo` also covers extension-generated repositories and repositories created
with `use_repo_rule`. [Mod command reference][modules]

An apparent repository name is interpreted relative to a repository's mapping.
A valid root-module name does not imply the same name is visible inside every
dependency. Record the referring repository and inspect its mapping/context before
renaming dependencies. [Repository mapping](../modules/repository-mapping.md)

Our recommendation: inspect the selected module, extension declaration, `use_repo`
imports, root overrides, and lockfile changes in that order. Do not repair every
missing label by adding another direct dependency: the failure may be a generated
repository import or an exported target name instead.
